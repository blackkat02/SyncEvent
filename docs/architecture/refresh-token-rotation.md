## 0. TL;DR / рішення

1. Поточна модель — **один `refreshToken`-хеш на юзера** (`User.refreshToken`). Це блокує мульти-сесії:
   логін з іншого пристрою перезаписує чужу активну сесію.
2. Цільова модель — **окрема таблиця `RefreshToken`**, один рядок = одна сесія/пристрій, `familyId`
   тримає ланцюжок ротацій.
3. **Ротація**: при кожному `/auth/refresh` старий рядок → `revoked: true`, новий рядок — та сама `familyId`.
4. **Reuse-detection**: якщо пред'явлено токен, у якого в БД `revoked: true` — це ознака крадіжки/повторного
   використання → відкликати **всю family**, примусовий логаут цієї сесії.
5. **Logout**: `clearCookie` (клієнт) + `revoked: true` конкретного рядка в БД (сервер) — обидві дії разом.
6. **Access-токен не відкликається на сервері** (stateless JWT, 15 хв) — це свідомий компроміс, не баг.
   Справжня межа безпеки — refresh-шар.
7. **Відомий race condition**: паралельні запити на протухлий access → кожен сам робить `/refresh` з тим самим
   ще-не-ротованим токеном → другий запит бачить уже `revoked` → хибне спрацювання reuse-detection →
   легітимного юзера розлогинює. Лікується (а) single-flight на фронтенді, (б) grace-period на бекенді.

## 1. Поточний стан коду (як є зараз)

`auth.service.ts`:
- `getTokens` — видає `accessToken` (15хв, `JWT_SECRET`) + `refreshToken` (7д, `JWT_REFRESH_SECRET`).
- `updateRefreshToken` — хешує (`bcrypt`) і **перезаписує** єдине поле `User.refreshToken`.
- `refreshTokens(userId, refreshToken)` — читає `user.refreshToken`, `bcrypt.compare`, якщо збіг — видає нову
  пару і знову перезаписує те саме поле (ротація вже є, але на рівні одного поля).

`auth.controller.ts`:
- `setRefreshTokenCookie` — `httpOnly`, `secure` (prod), `sameSite: 'lax'`, `maxAge: 7d`.
- `/auth/refresh` — читає кукі, верифікує JWT-підпис, викликає `authService.refreshTokens`, ставить нову кукі.
- **Немає `/auth/logout`.**

Наслідок: ротація вже неявно "ігнорує" стару кукі (новий хеш перезаписує старий, `bcrypt.compare` старого
токена після ротації провалиться) — але тільки в межах **однієї** активної сесії на юзера. Другий логін
(інший пристрій) тихо вбиває першу сесію, хоча її кукі ще не протухла.

## 2. Проблеми поточної моделі

| # | Проблема | Наслідок |
|---|---|---|
| 1 | Один `refreshToken` на юзера | Немає мульти-девайсу: другий логін вбиває першу сесію |
| 2 | Немає `/auth/logout` | Кукі можна прибрати з браузера, але сервер токен ще 7д вважає дійсним |
| 3 | Reuse старого токена просто відхиляється (401), сесія власника нового токена не чіпається | Немає сигналу компрометації — крадіжку кукі не видно і не лікується |
| 4 | Немає TTL-очистки/ревокації в БД | Протухлі/відкликані токени не приберуться самі |
| 5 | (Цільова архітектура) Строга ротація без страховки від паралельних запитів | False-positive лог-аут живих юзерів при кількох одночасних вкладках/запитах |

## 3. Цільова схема

```prisma
model RefreshToken {
  id         String   @id @default(cuid())
  userId     String
  tokenHash  String                    // хеш КОНКРЕТНОГО токена цього рядка (не спільний!)
  familyId   String                    // спільний для всього ланцюжка ротацій одного логіну/пристрою
  revoked    Boolean  @default(false)
  expiresAt  DateTime
  createdAt  DateTime @default(now())
  userAgent  String?                   // опційно, для UI "активні сесії"
  user       User     @relation(fields: [userId], references: [id])

  @@index([familyId])
  @@index([userId])
}
```

`User.refreshToken` (старе поле) — видалити після міграції.

Один рядок = одна сесія на одному пристрої. Логін з іншого пристрою створює **новий** рядок з новою
`familyId`, не чіпаючи існуючі.

## 4. Потоки

### 4.1. Login / Register
- Створити новий рядок `RefreshToken` з новою `familyId` (напр. `cuid()` того ж рядка).
- Кукі містить сирий refresh-токен (JWT або opaque-рядок — TBD, див. §7); у БД — тільки хеш.

### 4.2. Refresh (нормальний випадок)
1. Знайти рядок за `familyId` (з payload токена) — не за самим токеном напряму, щоб зробити reuse-detection
   дешевим (один `SELECT` за індексом).
2. `bcrypt.compare` пред'явленого токена з `tokenHash` знайденого рядка.
   - Не збігається, але рядок `revoked === false` → щось не так (токен підроблений/чужий) → 401,
     сесію не чіпати.
   - Не збігається, і рядок `revoked === true` → **reuse-detection**, див. 4.4.
   - Збігається → ротація: цей рядок → `revoked: true`, створити новий рядок з тим самим `familyId`.
3. Видати нову пару токенів, оновити кукі.

### 4.3. Logout
1. `res.clearCookie('refreshToken')`.
2. Позначити рядок (за `familyId` з поточного токена) `revoked: true` в БД.
3. Access-токен сервер не чіпає (§0.6) — фронтенд сам прибирає його зі свого стору/пам'яті.

### 4.4. Reuse-detection (підозра на крадіжку)
Пред'явлено токен, що матчить **уже відкликаний** рядок з `revoked: true`:
1. Відкликати **всі** рядки з цією `familyId` (не тільки знайдений).
2. 401 у відповідь, кукі очистити.
3. (Опційно, не в MVP) залогувати інцидент / повідомити юзера email'ом "нова підозріла активність".

## 5. Race condition при паралельному refresh — і чому строга reuse-detection його ловить хибно

Сценарій: кілька вкладок або кілька одночасних фонових запитів ловлять протухлий access-токен одночасно
і кожен сам ініціює `/auth/refresh` тим самим (ще дійсним на момент відправки) refresh-токеном з кукі.

| Крок | Запит A | Запит B |
|---|---|---|
| 1 | читає кукі (token v1) | читає кукі (token v1) |
| 2 | `/refresh` доїжджає першим | |
| 3 | сервер: v1 → `revoked`, видає v2, кукі оновлено | |
| 4 | | `/refresh` доїжджає з тим самим v1 |
| 5 | | сервер бачить v1 `revoked === true` → **reuse-detection** → відкликає всю family |
| 6 | юзер із живим v2 і живою сесією | **раптовий примусовий логаут**, хоча жодної крадіжки не було |

Це не гіпотетичний рідкісний edge case — трапляється щоразу, коли в застосунку кілька одночасних
API-викликів (типова SPA-поведінка: кілька віджетів фетчать дані паралельно) і access-токен саме
протух між ними.

### Мітигації (обидві потрібні, не одна)

1. **Single-flight на фронтенді** (головне виправлення). Усі паралельні запити, що впіймали 401,
   мають чекати на **один спільний** `/refresh`-проміс замість того, щоб кожен ініціював свій.
   Реалізація — axios/fetch interceptor з module-level `let refreshPromise: Promise<...> | null`:
   перший 401 створює проміс і виконує `/refresh`, усі наступні до resolve просто підписуються на
   той самий проміс і повторюють свій запит з новим accessToken після його завершення.
2. **Grace-period на бекенді** (страховка від мережевих затримок/ретраїв, які single-flight не ловить —
   напр. запит A завис на мережі і сервер уже встиг обробити B). Замість миттєвого `revoked: true → reuse`,
   дозволити **щойно-попередньому** (N-1) токену в ланцюжку ще ~5–10с повертати **той самий** новий
   accessToken/refreshToken пари N, а не тригерити повне відкликання family. Практично: не видаляти
   `tokenHash` попереднього рядка одразу, а тримати поле `supersededBy` + `supersededAt`; якщо пред'явлений
   токен матчить рядок із `supersededAt` не старшим за grace-вікно — віддати вже видану пару N ще раз
   (ідемпотентно), не створюючи нову ротацію і не викликаючи reuse-detection.

### Фаза 2 — анти-race ✅ (2026-09-13)
- [x] Фронтенд: single-flight interceptor для `/auth/refresh` (§5.1).
- [x] Бекенд: grace-period поле `supersededAt`/`supersededById`, N-1 токен ще прийнятний коротке вікно (§5.2).
- [x] Інтеграційний тест: N паралельних запитів з протухлим access → рівно один реальний `/refresh` на
  бекенді (або N, але жоден не тригерить reuse-detection) → юзера не розлогинило.

  Під час написання інтеграційного теста (справжня паралельність через `Promise.allSettled`, не
  симуляція) виявився реальний race поза межами того, що описано в §5: без атомарного
  compare-and-swap кілька одночасних запитів з тим самим **ще не проротованим** токеном усі проходили
  перевірку одночасно (жоден не встиг записати ротацію, поки інші читали) — family форкалась на N
  "живих" сесій, ламаючи інваріант "один активний рядок на family". Виправлено: дочірній рядок
  створюється до заявки на ротацію; сама заявка — атомарний `updateMany({id, revoked:false}, {revoked:
  true, supersededAt, supersededById})`; програвший видаляє свій щойно створений рядок і провалюється в
  grace/reuse-перевірку, де рядок переможця вже гарантовано існує (без вікна видимості).

## 7. Відкриті питання (ще не вирішено)

- **Формат самого refresh-токена**: лишити JWT (як зараз, підписаний `JWT_REFRESH_SECRET`, payload
  містить `familyId`) чи перейти на opaque random-рядок (менше даних "витікає" в самому токені, обов'язковий
  похід у БД на кожен refresh — але похід у БД потрібен у будь-якому разі для reuse-detection, тож JWT тут
  не дає виграшу в швидкості). Схиляюсь до **opaque** — простіше, не треба тримати `familyId` в
  JWT-payload синхронним зі схемою. **Не переглядалось під час реалізації Фаз 0-3** — лишили JWT
  (найменший diff), питання досі відкрите, якщо колись важливо буде мінімізувати дані в самому токені.
- **Grace-вікно (§5.2)** — конкретне значення (5с? 10с?) підібрати емпірично / за таймаутом фронтенд-реквестів.
  Реалізовано з `GRACE_PERIOD_MS = 10 * 1000` (верхня межа з озвученого діапазону) — досі не підбирали
  емпірично, просто взяли як стартове значення.
- Чи потрібен `familyId` окремим стовпцем, чи можна обійтись `id` першого рядка ланцюжка як "family root"
  (без окремого поля) — окреме поле явно читабельніше, лишаю в схемі.
