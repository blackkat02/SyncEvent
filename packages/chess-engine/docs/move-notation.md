# Запис ходів партії (нотація, історія, збереження)

Дизайн-документ для функціоналу запису ходів шахової партії: алгебраїчна
нотація (SAN), список ходів у UI, збереження в `localStorage`, експорт у PGN.

> **Статус (оновлено після впровадження власного шахового двигуна,
> `docs/move-validation.md`):** розділ 4 нижче більше не відкрите питання —
> вибір зроблено на користь **власного двигуна**, не `chess.js` (кроки 1-7
> того документа реалізовані й покриті тестами). Завдяки цьому розділ 6
> (SAN) одразу реалізований у **строгій** формі — "легкий MVP", який тут
> спершу описувався, пропущений повністю, бо повна легальність ходів
> (`getAllLegalMoves`) уже існувала, коли дійшла черга до нотації. Розділи
> 5, 7, 8 нижче оновлені під фактичний код; розділи 9-11 (localStorage зі
> схемою версій, PGN, undo) лишаються нереалізованими — статус позначено в
> кожному розділі окремо.

## 1. Мета

Зараз (`gameSlice.history`) ми зберігаємо лише сирі дії `{ from, to, piece }`.
Цього достатньо для відтворення дошки, але не для:

- показу гравцю читабельного списку ходів (`1. e4 e5 2. Nf3 Nc6`);
- експорту партії в PGN (щоб відкрити в lichess/chess.com або аналізаторі);
- коректного undo/перегляду попередніх позицій;
- майбутнього мультиплеєра/бота, яким потрібен однозначний запис ходу.

Документ описує: (1) яке архітектурне рішення прийняти для правил гри,
(2) модель даних ходу, (3) алгоритм побудови SAN, (4) зміни в Redux,
(5) UI-компонент списку ходів, (6) стратегію збереження в `localStorage`,
(7) PGN, (8) тестування та (9) поетапний план впровадження.

## 2. Поточний стан коду (as-is, історичний контекст)

> **Історичний розділ.** Таблиця нижче описує стан коду ДО впровадження
> `docs/move-validation.md`. Відтоді `gameSlice.js`/`gameOperations.js`
> суттєво змінились (повна валідація ходів; `captured`/`castling`/
> `enPassant`/`promotion`/`san`/`isCheck`/`isCheckmate` у кожному елементі
> `history`) — дивись розділ 5 нижче (оновлений) для фактичної моделі
> даних. Таблицю лишаємо без змін як пояснення мотивації рішень розділу 4.

| Файл | Роль зараз | Обмеження |
|---|---|---|
| `redux/game/gameSlice.js` | `moveExecuted` двигає фігуру, пушить `{from,to,piece}` в `history`, інкрементить `plyCount` | не знає, чи це взяття, чи це шах/мат, чи рокіровка/en passant/промоція |
| `redux/game/gameOperations.js` (`attemptMove`) | перевіряє лише чергу ходу, `from !== to`, friendly-fire | немає перевірки шляху фігури, шаху власному королю, взагалі "легальності" ходу за правилами шахів |
| `utils/boardUtils.js` | конвертація `'e2' ↔ {row, col}` | немає руху фігур/атак |
| `redux/store.js` | на кожен `store.subscribe` серіалізує **весь** `state.game` в `localStorage['chess_game_state']` | пише на **кожен тік годинника** (раз/сек), без версії схеми, без try/catch на читанні |

Важливий висновок: **у проєкті ще немає шахового "двигуна"** (генерації
легальних ходів, детекції шаху/мату). А коректний SAN критично залежить саме
від цього — наприклад, "Nbd7" (дизамбігуація) можливий лише тоді, коли знаєш,
що інший кінь дійсно міг би легально піти на те саме поле (в т.ч. не залишивши
свого короля під шахом).

## 3. Термінологія

- **Ply (напівхід)** — один хід одного гравця. `plyCount` у слайсі — це саме
  це поле.
- **Move (хід)** — пара напівходів (білі + чорні) з одним номером, як у записі
  партії (`1. e4 e5`).
- **SAN** (Standard Algebraic Notation) — `e4`, `Nbd7`, `O-O`, `exd5`, `e8=Q+`,
  `Qh5#`.
- **FEN** — рядок повної позиції (уже є `data/fenConstants.js`).
- **PGN** — текстовий формат партії: заголовки (`[White "..."]`) + список
  ходів у SAN.

## 4. Архітектурне рішення: своя логіка чи `chess.js` (вирішено)

Це рішення вже прийняте й реалізоване — розділ лишається нижче як пояснення
мотивації, а не як відкрите питання.

**Прийнято: власний двигун, без `chess.js`.** Детальний дизайн — окремий
документ `docs/move-validation.md` (геометрія фігур, шах/мат/пат, рокіровка,
взяття на проході, промоція); реалізація — `src/engine/*`. Аргумент, який
на момент першої версії цього документа виглядав як довід **за** `chess.js`
("SAN формально неможливо коректно згенерувати без повної генерації
легальних ходів") — насправді виявився доводом **за побудову власного
генератора**: цей генератор довелося писати в будь-якому разі для валідації
ходів (яка потрібна незалежно від нотації), і коли він з'явився, `chess.js`
більше не додавав жодної унікальної цінності для потреб цього проєкту.

Причини, з яких `chess.js` спершу здавався очевидним вибором (нижче —
історичний запис аргументів "за", актуальних на момент першої версії
документа):

- SAN формально неможливо коректно згенерувати без повної генерації легальних
  ходів (дизамбігуація, "чи хід не залишає свого короля під шахом", шах/мат).
- `chess.js` дає `.moves({ verbose: true })`, `.move()`, `.san`, `.pgn()`,
  `.fen()`, `.in_check()`, `.in_checkmate()` — закриває одразу й легальність,
  і нотацію, і PGN, без потреби писати щось із цього самостійно.
- Поточний Redux-стан (`board` як `{a2:'P',...}`) легко співіснував би з
  `chess.js` через FEN/SAN.

**Наслідок для цього документа:** "легкий алгоритм без повної легальності"
(розділ 6 у попередній версії) був **пропущений повністю** — до моменту,
коли дійшла черга писати SAN, `getAllLegalMoves`/`isCheck`/`isCheckmate`
уже існували й були протестовані (`docs/move-validation.md`, кроки 1-5),
тож одразу написана **строга** версія (розділ 6 нижче, оновлений).

## 5. Модель даних ходу (реалізовано, з відхиленнями від початкового ескізу)

`history` більше не сирий `{from, to, piece}` — кожен елемент тепер об'єкт,
який `gameSlice.js:moveExecuted` формує сам, похідно від payload'а ходу
(`docs/move-validation.md`, кроки 2, 4, 6, 7):

```js
// один елемент state.game.history — фактична форма (gameSlice.js)
{
  from: 'e2',
  to: 'e4',
  piece: 'P',            // FEN-символ фігури, що ходила
  captured: null,        // FEN-символ з'їденої фігури або null (крок 2)
  castling: null,        // 'K' (коротка) | 'Q' (довга) | null (крок 4)
  enPassant: false,      // true, якщо це взяття на проході (крок 4)
  promotion: null,       // 'Q' | 'R' | 'B' | 'N' | null (крок 6)
  isCheck: false,        // статус СУПЕРНИКА одразу після ходу (крок 7)
  isCheckmate: false,
  san: 'e4',             // готовий SAN-рядок (крок 7, розділ 6 нижче)
}
```

**Відхилення від початкового ескізу вище — свідомі, не забуті:**

- **`ply` не зберігається окремим полем.** Номер напівходу — це просто
  позиція елемента в масиві `history` (`index + 1`); `selectMovePairs`
  (розділ 7) рахує номер ходу через `pairs.length + 1` під час групування,
  без потреби дублювати це число в кожному об'єкті.
- **`color` не зберігається окремим полем.** Колір фігури, що ходила,
  однозначно визначається з `piece` через уже наявний `getPieceColor`
  (регістр FEN-символу) — окреме поле дублювало б інформацію, яка й так є.
- **`fenAfter` і `timestamp` не додані.** Обидва потрібні лише для функцій,
  які ще не реалізовані: перегляд історії/undo (розділ 11) і майбутній
  таймлайн ходів. Додавати їх зараз означало б тримати в `history` дані, які
  ніхто не читає — суперечило б принципу "не проєктувати наперед".

`captured` захоплюється до мутації **всередині самого редюсера**
(`docs/move-validation.md`, крок 2) — так, як і передбачав цей розділ
у початковій версії.

## 6. Логіка формування SAN (реалізовано — строга версія, `src/engine/notation.js`)

Легка версія, що первісно планувалась тут (SAN без урахування шаху власному
королю в дизамбігуації, без суфіксів `+`/`#`), була пропущена повністю —
див. розділ 4. Реальна реалізація одразу строга, бо спирається на вже готовий
генератор легальних ходів (`docs/move-validation.md`, кроки 1-5):

```js
// src/engine/notation.js
export function buildSan(gameStateBeforeMove, move, status = {}) {
  const { from, to, piece, captured, castling, promotion } = move;
  const { isCheck = false, isCheckmate = false } = status;

  let san;
  if (castling === 'K') san = 'O-O';
  else if (castling === 'Q') san = 'O-O-O';
  else {
    const pieceType = piece.toUpperCase();
    const isCapture = Boolean(captured);

    if (pieceType === 'P') {
      san = isCapture ? `${from[0]}x${to}` : to;
      if (promotion) san += `=${promotion}`;
    } else {
      const disambiguation = getDisambiguation(gameStateBeforeMove, move);
      san = `${pieceType}${disambiguation}${isCapture ? 'x' : ''}${to}`;
    }
  }

  if (isCheckmate) san += '#';
  else if (isCheck) san += '+';
  return san;
}
```

Ключова відмінність від початкового ескізу: **дизамбігуація питає в
справжнього генератора легальних ходів** (`getAllLegalMoves`), а не
геометрично наближеної функції — фігура, яка технічно могла б дійти до тієї
ж клітинки, але залишила б власного короля під шахом, коректно
**виключається** з кандидатів на дизамбігуацію (`getDisambiguation` у
`notation.js` фільтрує кандидатів саме через `getAllLegalMoves`, а не через
геометрію в ізоляції). Суфікси `+`/`#` рахуються через `isCheck`/`isCheckmate`
(`docs/move-validation.md`, крок 5) для стану **суперника одразу після
ходу** — тобто вони більше не "недоступні до `chess.js`", як казала
попередня версія цього розділу, а працюють одразу.

Виклик відбувається не в `gameOperations.js` (як спершу планувалось), а
**всередині самого редюсера** `gameSlice.js:moveExecuted`, поруч із рештою
похідних фактів про хід (`captured`, `castling`, `enPassant`, `promotion`) —
детальне пояснення цього архітектурного рішення (і чому статус мату
рахується двічі: тут для суфікса SAN, і окремо в `gameOperations.js` для
`endGame`) дивись у коментарях самого файлу.

Тести: `src/engine/notation.test.js` — тихий хід, взяття, дизамбігуація по
файлу/рангу/повним полем (включно з "три фігури на дотичних лініях" — edge
case, згаданий у попередній версії цього розділу), рокіровка, промоція (з
узяттям і без), суфікси `+`/`#`.

## 7. Redux: зміни (реалізовано, `gameSlice.js`/`gameSelectors.js`)

- `gameSlice.moveExecuted`: **не** приймає вже розширений payload ззовні —
  усе ще отримує мінімальний `{from, to, piece, promotion?}` від
  `attemptMove` і сам **обчислює** решту (`captured`, `castling`,
  `enPassant`, `promotion`, `san`, `isCheck`, `isCheckmate`) прямо в тілі
  редюсера, перш ніж пушити готовий об'єкт у `history` (розділ 5). Це
  відрізняється від початкового формулювання цього пункту ("приймає
  розширений payload") — на практиці розширення відбувається **всередині**
  редюсера, а не до його виклику.
- Селектори в `gameSelectors.js` (фактичний код, трохи відрізняється від
  ескізу — немає окремого поля `color`, колір визначається з `piece`):
  ```js
  export const selectMoveHistory = (state) => state.game.history;

  export const selectMovePairs = (state) =>
    state.game.history.reduce((pairs, move) => {
      if (getPieceColor(move.piece) === COLORS.WHITE) {
        pairs.push({ number: pairs.length + 1, white: move, black: null });
      } else if (pairs.length > 0) {
        pairs[pairs.length - 1].black = move;
      }
      return pairs;
    }, []);
  ```
  Захист `pairs.length > 0` — не з початкового ескізу; доданий тому, що
  `gameOperations.js` має "аналіз без правил" режим (вільні ходи після
  `isGameOver`), де черга кольорів формально не гарантована.
- `selectCurrentTurn` дійсно не змінився — усе ще похідне від `plyCount`.

## 8. UI: компонент списку ходів (реалізовано)

`src/components/MoveList/MoveListContainer.jsx` +
`src/components/MoveList/MoveListView.jsx` — той самий патерн
container/view, що й `ChessBoardContainer`/`ChessBoardView`.

Відхилення від ескізу:

- Автоскрол прив'язаний до `movePairs.length` (кількість пар), не до
  `plyCount` — обидва змінюються синхронно, але `movePairs.length` ближче до
  того, що фактично рендериться.
- `onSelectPly` **не реалізований** — клік по ходу поки нічого не робить;
  перегляд історії (розділ 11) досі не впроваджений, тож немає що викликати
  на клік.
- Розміщення тепер не просто "бічна панель поруч із дошкою" —
  `MoveListContainer` один з трьох рівноправних розділів адаптивного
  3-колонкового макета `HomePage.jsx` (інфо про гравців | дошка | список
  ходів на десктопі; окрема розкладка для планшета й мобілки). Список ходів
  заповнює всю висоту своєї колонки на десктопі (`h-full`/`flex-1`/
  `min-h-0`) і прокручується всередині себе, не розтягуючи всю сторінку.

## 9. Збереження в `localStorage`

**Статус: не реалізовано.** `redux/store.js` досі використовує наївний
підхід, описаний нижче як проблема — жодна з пропозицій цього розділу
(throttle, версія схеми, симетричне читання) ще не впроваджена. `history`
тепер має форму, готову для збереження (розділ 5), тож ключове блокування
знято — лишається сама робота.

Поточна реалізація (`redux/store.js`) — робочий, але вразливий підхід:

```js
store.subscribe(() => {
  localStorage.setItem('chess_game_state', JSON.stringify(store.getState().game));
});
```

Проблеми й рекомендації:

1. **Пише на кожен `dispatch`, включно з тіком годинника (раз/сек).**
   → Дебаунсити запис (наприклад, `throttle` 1000 мс вже фактично збігається
   з тіком, але краще розділити: миттєвий запис на `moveExecuted`/`endGame`,
   і throttled запис (кожні ~5с) для `updateTime`, щоб не гамселити диск/квоту
   без потреби.
2. **Немає версії схеми.** Якщо завтра зміниться форма `history` (розділ 5),
   старий збережений стан із продакшену зламає додаток при `JSON.parse` +
   підстановці в Redux (поля не будуть відповідати очікуваним).
   → Зберігати обгортку:
   ```js
   const STORAGE_KEY = 'chessb:v1:game';
   const payload = { version: 1, state: store.getState().game };
   localStorage.setItem(STORAGE_KEY, JSON.stringify(payload));
   ```
   При завантаженні — перевіряти `version`; якщо не збігається з поточною —
   ігнорувати збережений стан (почати нову партію) замість краху.
3. **Немає обробки помилок при читанні** (лише запис обгорнутий в try/catch).
   Потрібна симетрична функція `loadPersistedGame()` з try/catch навколо
   `JSON.parse`, яка повертає `undefined` при будь-якій помилці (пошкоджені
   дані, quota-помилки, приватний режим браузера без доступу до
   `localStorage`).
4. **PGN не варто зберігати окремим рядком-дублікатом.** Джерело істини —
   масив `history` (розділ 5); PGN будується з нього на льоту (розділ 10).
   Дублювання = ризик розсинхронізації.
5. **Ключ спільний для "поточна партія" й потенційно "налаштування".** Якщо
   згодом з'явиться щось на кшталт збережених налаштувань UI — використати
   окремий ключ (`chessb:v1:settings`), не мішати в один об'єкт з ігровим
   станом.

Підсумкова структура ключа:

```js
localStorage['chessb:v1:game'] = JSON.stringify({
  version: 1,
  savedAt: Date.now(),
  state: { board, history, plyCount, whiteTime, blackTime, playerSide, gameId, winner, reason, isGameOver },
});
```

## 10. PGN: експорт/імпорт

**Статус: не реалізовано.** `src/utils/pgn.js` не існує. Дизайн нижче
лишається чинним — `history` вже має всі потрібні поля (зокрема `san`).

Похідна функція (не зберігається, будується за запитом):

```js
// src/utils/pgn.js
export function buildPgn(history, meta = {}) {
  const headers = [
    `[Event "${meta.event ?? 'Casual game'}"]`,
    `[Date "${meta.date ?? new Date().toISOString().slice(0, 10)}"]`,
    `[White "${meta.white ?? 'Player'}"]`,
    `[Black "${meta.black ?? 'Player'}"]`,
    `[Result "${meta.result ?? '*'}"]`,
  ].join('\n');

  const movesText = movePairsToPgnBody(history); // "1. e4 e5 2. Nf3 Nc6 ..."
  return `${headers}\n\n${movesText} ${meta.result ?? '*'}`;
}
```

UI: кнопка "Копіювати PGN" / "Завантажити .pgn" у панелі списку ходів
(`navigator.clipboard.writeText` + `Blob` + посилання-завантаження). Це не
потребує нових залежностей і одразу дає сумісність із lichess/chess.com для
імпорту.

## 11. Undo / перегляд історії ходів

**Статус: не реалізовано.** Обидва сценарії нижче вимагають поля `fenAfter`
(розділ 5), якого немає в поточній моделі ходу — свідомо відкладено, доки
не з'явиться конкретна потреба (див. розділ 5, "Відхилення від початкового
ескізу").

Два різні за складністю сценарії — варто розрізняти в майбутньому плануванні:

- **Перегляд минулої позиції (read-only, без зміни `plyCount`)**: клік по
  ходу в `MoveList` показує `fenAfter` цього ходу на дошці в окремому
  "viewing mode", не чіпаючи справжній ігровий стан. Найдешевше рішення:
  використовувати вже запропоноване поле `fenAfter` (розділ 5) +
  `fenConverter.js`, який уже є в проєкті.
- **Справжній undo (зміна ігрового стану)**: обрізати `history` до потрібного
  `ply`, відновити `board` з `fenAfter` попереднього ходу (або з
  `initialBoardPiecesObject`, якщо відкат до старту), відкоригувати
  `plyCount`. Складніше через годинники (скільки часу повернути гравцю?) —
  залишити поза MVP, окремим рішенням продукту, чи потрібен undo в грі з
  таймером взагалі (у змагальних шахах undo зазвичай відсутній).
