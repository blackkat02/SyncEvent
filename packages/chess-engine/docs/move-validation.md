# Валідація ходів без `chess.js` (власний шаховий двигун)

Дизайн-документ для власної, незалежної від сторонніх бібліотек логіки
валідації шахових ходів: геометрія фігур, шах/мат/пат, рокіровка, взяття на
проході, промоція. `docs/move-notation.md` (розділ 4) рекомендував підключити
`chess.js` саме тому, що коректна нотація й легальність ходів вимагають
повноцінного "двигуна". Цей документ описує, як побудувати такий двигун
самостійно, покроково, від найпростіших примітивів до повної легальності.

> **Статус: кроки 0–7 реалізовані й покриті тестами** (139 тестів:
> `src/engine/*.test.js`, `src/redux/game/*.test.js`). Крок 8 (нічиї)
> свідомо не реалізований — лишається поза MVP. Розділ 5 нижче позначає
> кожен крок окремо; розділи 2–4 лишені в первісному, "проєктному" вигляді
> (звідси невідповідність часу дієслів — "потрібно зробити" про те, що вже
> зроблено), з точковими виправленнями там, де фактична реалізація
> відхилилась від плану.

## 1. Мета

Дати відповідь на питання "чи є хід `from → to` легальним ходом за правилами
шахів у поточній позиції" — без залежності від `chess.js` чи іншої бібліотеки.
Це базовий примітив, на якому будується все інше:

- заборона ходів, що порушують геометрію фігури (пішак не має ходити як ферзь);
- заборона ходів "крізь" інші фігури (для тури, слона, ферзя);
- заборона ходів, що залишають власного короля під боєм;
- рокіровка, взяття на проході, промоція пішака;
- визначення шаху, мату, пату — для коректного завершення партії та для
  суфіксів `+`/`#` у нотації (`docs/move-notation.md`, розділ 6).

## 2. Поточний стан гри в Redux (as-is)

### 2.1 Форма стану (`gameSlice.js`)

```js
{
  board: { a2: 'P', e4: 'p', ... },  // плоский об'єкт 'клітинка' -> FEN-символ
  selectedSquare: null,
  whiteTime: 180000,
  blackTime: 180000,
  history: [],                       // { from, to, piece } — сирі дії, без captured/castling/enPassant
  plyCount: 0,                       // хід = похідне: WHITE якщо plyCount % 2 === 0
  winner: null,
  reason: null,
  isGameOver: false,
  playerSide: 'w',
  gameId: 0,
}
```

**Чого немає в стані, хоча правила шахів цього вимагають:**

| Поле | Навіщо потрібне | Де вже є "натяк" на нього |
|---|---|---|
| `castlingRights` (`{ wK, wQ, bK, bQ }` або рядок `'KQkq'`) | Рокіровка дозволена, лише поки король і відповідна тура жодного разу не рухались | `fenConstants.STARTING_FEN` містить `KQkq`, але `positions.js:7` бере лише `split(' ')[0]` — все інше відкидається |
| `enPassantTarget` (клітинка або `null`) | Взяття на проході легальне лише один напівхід після ходу пішака на 2 клітинки | Немає навіть заготовки |
| Позиції королів (`kingPositions: { w: 'e1', b: 'e8' }`) | Швидка перевірка шаху без сканування всієї дошки щоразу | Немає — довелось би шукати `'K'`/`'k'` лінійним проходом по `board` |
| `halfmoveClock` / `fullmoveNumber` | Правило 50 ходів, нумерація партії в PGN | Є в `STARTING_FEN`, відкидається так само як `castlingRights` |

### 2.2 Поточна "валідація" ходу (`gameOperations.js:7-52`, `gameSelectors.js:60-68`)

Реальна перевірка легальності зараз складається лише з:

1. `getPieceColor(piece) !== turn` — хід не за чергою.
2. `from === to` — клік у ту саму клітинку.
3. `selectIsFriendlyFire` — не бити фігуру свого кольору.

**Немає жодної перевірки геометрії фігури.** Це означає, що на практиці зараз
(до цього документа) пішак може "ходити" на будь-яку вільну чи ворожу
клітинку дошки, тура — по діагоналі, кінь — крізь інші фігури як завгодно;
єдине, що зупиняє гравця — UI, який може взагалі не обмежувати клік. Це
головна діра, яку закриває розділ 5 (крок 1).

`captured` фігура також ніде не зберігається (`moveExecuted` просто
перезаписує `state.board[to] = piece`, стара фігура на `to` губиться) —
важливо для `docs/move-notation.md` (SAN, розділ 5), тому крок 2 нижче
захоплює її до мутації.

### 2.3 Висновок

Проєкт зараз має лише "координатну арифметику" (`boardUtils.js`) та
"хто якого кольору" (`chessHelpers.js`). Немає жодного з трьох базових шарів
шахового двигуна: (a) генерація псевдолегальних ходів фігури, (b) детекція
атаки на клітинку, (c) фільтрація по безпеці для власного короля. Документ
нижче будує їх у цьому самому порядку.

## 3. Теоретичне обґрунтування

### 3.1 Псевдолегальні vs легальні ходи

- **Псевдолегальний хід** — відповідає геометрії фігури й не натикається на
  свою фігуру дорогою (для фігур, що ковзають). Не враховує стан шаху.
- **Легальний хід** — псевдолегальний хід, який після виконання **не залишає
  власного короля під шахом**.

Практичний алгоритм генерації легальних ходів завжди двоетапний:
`легальні = псевдолегальні.filter(хід => !залишаєКороляПідШахом(хід))`.
Це не оптимально (O(ходи × перевірка_шаху)), але для звичайної гри людини
(не для рушія, що рахує мільйони позицій на секунду) продуктивність
абсолютно достатня — оптимізації (bitboards, pin-detection без грубої сили)
не потрібні на цьому етапі.

### 3.2 Геометрія фігур — дві категорії

- **"Крокуючі" (steppers):** король, кінь. Фіксований набір зміщень
  `(dRow, dCol)`, кожне перевіряється незалежно, дорога не має значення.
  - Кінь: `[(±1,±2), (±2,±1)]` — 8 зміщень.
  - Король: усі 8 сусідніх клітинок `(dRow,dCol) ∈ {-1,0,1}², крім (0,0)`.
- **"Ковзаючі" (sliders):** тура, слон, ферзь. Набір напрямків, у кожному
  напрямку йдемо клітинка за клітинкою, поки не вийшли за межі дошки, не
  зустріли свою фігуру (стоп, не включаючи її) або ворожу (стоп, включаючи —
  це взяття).
  - Тура: 4 напрямки (вертикаль/горизонталь).
  - Слон: 4 напрямки (діагоналі).
  - Ферзь: об'єднання напрямків тури й слона (8 напрямків).
- **Пішак — окремий випадок**, не вкладається в жодну категорію:
  - Хід вперед на 1 клітинку — тільки якщо клітинка порожня.
  - Хід вперед на 2 клітинки — тільки з початкового ряду (2-й для білих,
    7-й для чорних) і тільки якщо **обидві** клітинки попереду порожні.
  - Взяття по діагоналі на 1 клітинку — тільки якщо там ворожа фігура **або**
    це клітинка взяття на проході (розділ 3.4).
  - Напрямок руху залежить від кольору (білі — до зменшення rank-індексу
    в системі координат `boardUtils.js`, тобто "вгору" по дошці; чорні —
    навпаки).
  - Промоція при досягненні останнього ряду (розділ 3.5).

Це єдиний блок, що відрізняється між кольорами — решта геометрії кольоронезалежна.

### 3.3 Детекція атаки на клітинку — ключовий перевикористовуваний примітив

Функція `isSquareAttacked(board, square, byColor)` — "чи атакує колір
`byColor` клітинку `square` в поточній позиції" — це не просто допоміжна
функція для шаху. Вона потрібна **тричі** для різних правил:

1. **Шах:** король під шахом ⟺ `isSquareAttacked(board, kingSquare, opponentColor)`.
2. **Легальність ходу короля:** король не може піти на клітинку, атаковану
   суперником (навіть якщо там немає фігури, яка б "брала" короля прямо
   зараз — важливо для рокіровки та звичайних ходів короля).
3. **Рокіровка:** король не може ні стояти під шахом, ні проходити через
   атаковану клітинку, ні приземлятись під шах (розділ 3.4).

Реалізується як генерація псевдолегальних ходів **для кожного типу фігури
кольору `byColor`**, але "навпаки" — не "куди може піти", а "чи входить
`square` у список клітинок, які фігура цього типу б'є". Для пішака це
відрізняється від його ходу (пішак атакує по діагоналі, навіть якщо там
порожньо; хід вперед — не атака). Тому атаки пішака рахуються окремою
функцією, не через `getPawnMoves`.

Важливий нюанс продуктивності й коректності: коли рахуємо, чи король
буде під шахом **після** гіпотетичного ходу, потрібно рахувати атаки на
дошці **після** цього ходу (з переміщеною/знятою фігурою), а не на поточній.
Найпростіша коректна реалізація: зробити хід на **копії** `board` (плоский
об'єкт — дешево копіювати через spread), перевірити `isSquareAttacked`,
відкинути копію. Мутувати справжній `state.board` для перевірки не можна.

### 3.4 Спеціальні правила

**Рокіровка.** Легальна, коли одночасно:
1. Ні король, ні відповідна тура ще не рухались (`castlingRights`).
2. Усі клітинки між королем і турою порожні.
3. Король не стоїть під шахом зараз.
4. Король не проходить через жодну атаковану клітинку (включно з кінцевою).

Наслідок: рокіровку не можна виразити як "звичайний" псевдолегальний хід
короля на 2 клітинки, відфільтрований загальним правилом "не залишати короля
під шахом" — пункт 4 (клітинка, яку король лише **перетинає**) не
перевіряється для жодного іншого ходу. Це окрема, явно виписана функція
`getCastlingMoves`, не частина `getKingMoves`.

**Взяття на проході (en passant).** Легальне на клітинці `enPassantTarget`
лише одразу після того, як суперник щойно пішов пішаком на 2 клітинки —
тобто це `state`, що живе рівно один напівхід і обнуляється після будь-якого
іншого ходу. Реалізується так само, як у FEN: окреме поле в стані гри
(розділ 4.1), не похідне від `history` "на льоту" (хоча технічно можна й так
— `history[history.length-1]`, — але явне поле простіше й ближче до FEN,
що вже присутній у проєкті як формат).

**Промоція.** Пішак, що доходить до останнього ряду, обов'язково
перетворюється (типово: гравець обирає фігуру — UI-питання, поза межами
цього документа; двигун лише повертає прапорець "цей хід вимагає промоції"
і приймає обрану фігуру як параметр ходу).

### 3.5 Шах, мат, пат

Формальні визначення (стандартні, для реалізації буквально):

- **Шах:** `isSquareAttacked(board, kingSquare(color), opponent(color))`.
- **Легальний хід існує:** `generateAllLegalMoves(board, color).length > 0`.
- **Мат:** шах І немає жодного легального ходу.
- **Пат:** немає шаху І немає жодного легального ходу (нічия).

Обидва визначення використовують один і той самий примітив
`generateAllLegalMoves` — окремого "алгоритму детекції мату" не існує, це
побічний ефект того, що генерація легальних ходів уже враховує безпеку
короля (розділ 3.1).

### 3.6 Що свідомо залишаємо поза MVP

- Нічия за 50 ходів без взяття/ходу пішака (`halfmoveClock`) — легко додати
  пізніше, вимагає лише лічильника в стані, не впливає на архітектуру ходів.
- Нічия через повторення позиції тричі — вимагає історії FEN/hash позицій
  для порівняння; більше "продуктова" фіча, ніж частина валідації ходу.
- Нічия через недостатність матеріалу (KvK, KvKN, KvKB) — статична перевірка
  фігур на дошці, не залежить від ходів.

Жодне з них не блокує розділи 4–5 нижче; вони додаються останніми
(розділ 6, крок 6+) без зміни вже збудованої архітектури.

## 4. Архітектурне рішення

### 4.1 Розширення стану гри (реалізовано частково — свідомо)

Додано в `gameSlice.js` `initialState`:

```js
{
  // ...наявні поля...
  castlingRights: { wK: true, wQ: true, bK: true, bQ: true },  // ✅ реалізовано
  enPassantTarget: null,       // 'e3' або null                 // ✅ реалізовано
}
```

**`kingPositions` НЕ додано в стан** — свідоме рішення, не пропуск. Замість
кешованої позиції короля використовується лінійний пошук по `board`
(`findKingSquare(board, color)` у `src/engine/legalMoves.js`, перевикористаний
і в `gameStatus.js`). Цей самий абзац і дозволяв цей вибір ("оптимізація, не
обов'язкова концептуально") — обрано простіший варіант, щоб не торкатися
схеми стану без реальної потреби в продуктивності (дошка ≤32 фігури, гра
людини, не рушій, що прораховує мільйони позицій на секунду).

### 4.2 Структура модулів (реалізовано, з двома додатковими файлами)

```
src/engine/
  pieceGeometry.js   // ✅ геометрія фігур: зміщення коня/короля, напрямки слайдерів
  pseudoMoves.js      // ✅ генерація псевдолегальних ходів для 1 фігури на 1 клітинці
  attacks.js          // ✅ isSquareAttacked(board, square, byColor)
  legalMoves.js        // ✅ фільтр псевдолегальних → легальні + рокіровка (getCastlingMoves) + findKingSquare
  gameStatus.js        // ✅ isCheck / getAllLegalMoves / isCheckmate / isStalemate
  promotion.js         // ✅ додано поза початковим списком: requiresPromotion/resolvePromotionPiece (крок 6)
  notation.js          // ✅ додано поза початковим списком: buildSan (крок 7, docs/move-notation.md)
  index.js             // ⬜ фасад лишився заглушкою — див. розділ 4.3
```

`promotion.js` і `notation.js` не були в первісному списку цього розділу —
на момент його написання кроки 6–7 ще не були настільки конкретними.
Обидва відповідають тому самому принципу "чисті функції, без Redux".
`notation.js` живе саме тут, а не в `src/utils/`, як спершу пропонував
`docs/move-notation.md`, — дизамбігуація SAN залежить від `getAllLegalMoves`,
тобто це логіка рушія, а не загальна утиліта.

Кожен модуль — чисті функції `(board, ...) => результат`, що приймають
`board`-об'єкт (і за потреби `castlingRights`/`enPassantTarget`) як аргументи,
а не читають Redux-стан напряму. Це дозволяє:
- юніт-тестувати без Redux/React (так само, як `boardUtils.test.js`);
- перевикористати ту саму логіку і в `gameOperations.js` (перевірка перед
  диспатчем), і в майбутньому боті/аналізаторі ходів, і в `notation.js`
  (`docs/move-notation.md`, розділ 6) для дизамбігуації, яка тепер
  **строга** (з урахуванням шаху власному королю), а не "легка".

### 4.3 Точка інтеграції (реалізовано інакше, ніж тут заплановано)

Фактичний `gameOperations.js:attemptMove` **не** використовує фасад
`engine/index.js` (`isMoveLegal`/`getMoveDetails` лишились незаповненими
заглушками з кроку 0) — натомість імпортує потрібні функції рушія напряму:

```js
import { getPseudoLegalMoves } from '../../engine/pseudoMoves';
import { filterByKingSafety, getCastlingMoves } from '../../engine/legalMoves';
import { isCheckmate, isStalemate } from '../../engine/gameStatus';
import { requiresPromotion, isValidPromotionPiece } from '../../engine/promotion';
```

Це працює й покрито тестами (`gameOperations.test.js`), але означає, що
`attemptMove` "знає" більше деталей рушія, ніж малося на увазі цим
розділом — консолідація за фасадом `getMoveDetails`, яку тут пропонували,
лишається нездійсненим рефакторингом на майбутнє (нічого зараз не блокує).

`selectIsFriendlyFire`/`selectIsMovePossible` дійсно не видалені, як тут і
передбачалось, — але й підсвітка легальних клітинок через `getAllLegalMoves`
теж не реалізована (такої UI-фічі поки що взагалі немає), тож ця пропозиція
лишається чинною ідеєю на майбутнє, не зробленою роботою.

### Крок 1 — геометрія й псевдолегальні ходи ✅ реалізовано (найважливіший крок; закриває головну діру з розділу 2.2)
1. `pieceGeometry.js`: константи зміщень коня/короля, напрямків
   тури/слона/ферзя.
2. `pseudoMoves.js`: `getPseudoLegalMoves(board, square)` — диспетчер по типу
   фігури (`piece.toUpperCase()`), що повертає масив клітинок `to`, куди
   фігура **геометрично** може піти (з урахуванням своїх/чужих фігур на
   шляху, без урахування шаху). Пішак — окрема функція `getPawnMoves`
   (розділ 3.2), включно зі "стрибком на 2" і взяттям (поки без en passant —
   він додається в кроці 5, коли з'явиться `enPassantTarget`).
3. **Одразу інтегрувати в `attemptMove`** (без кроків 2–4) як заміну
   відсутньої зараз перевірки геометрії:
   `if (!getPseudoLegalMoves(board, from).includes(to)) return;`
   Це вже прибирає найгрубіший баг (пішак/тура/слон, що ходять як завгодно)
   **до** того, як з'явиться повна перевірка шаху. Свідомий проміжний стан:
   ще можна залишити свого короля під шахом — прийнятно для кількох днів
   розробки, неприйнятно як фінальний реліз.

Тести: для кожного типу фігури — кут дошки, центр дошки, фігура заблокована
своєю/чужою фігурою, порожня дошка (fixtures на кшталт `MATE_IN_ONE_FEN` у
`fenConstants.js`, тільки простіші — по одній фігурі на дошці).
